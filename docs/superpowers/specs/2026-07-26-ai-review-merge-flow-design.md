# AIレビュー統合フロー 設計

日付: 2026-07-26
ステータス: 承認待ち

## 背景と目的

現行のPRレビューフローは、`review` / `review-subagents`(`shell/zsh/alias/ai/ai.zsh`)がherdrの複数タブでClaude / Gemini / Codexを起動し、各AIが統一フォーマットで指摘を出力、ユーザーが各タブを目視で巡回して重複を頭の中でマージし、採用番号をメモして `pr-comment-post` に渡す、というもの。

主な苦痛:

1. 3タブの巡回と読み比べ
2. AI間の重複指摘を脳内で統合する作業
3. 採用番号のメモ→投稿の引き継ぎ
4. セルフレビュー時も一度PRコメント投稿を経由してから自分で対応する遠回り

対応要否の判断はユーザーが行う(自動化しない)。3AI並列レビュー構成は維持する。

## 全体フロー

```
既存(改修): review / review-subagents
  ├─ タイムスタンプ付きの新規ランディレクトリを作成し latest リンクを更新
  ├─ 3AIとも新規タブでレビュー起動 + 結果をランディレクトリへ書き出し
  │   (Claudeも新規タブへ変更。従来はコマンドを打ったタブがClaudeになっていた)
  └─ 元のタブ: フォアグラウンドのウォッチャーが完了を監視
        ↓ 全結果ファイルが揃ったら、同じタブで review-merge を自動起動
新規: review-merge スキル (Claude / Codex)
  → 3結果ファイルを意味ベースで重複統合
  → merged.json + report.html 生成、ブラウザで自動オープン
        ↓ ユーザーがHTML上で確認・「対応する」チェック
  state.json (ブラウザが自動保存)
        ↓
新規: review-post スキル        新規: review-fix スキル
  (他人のPR: 採用項目を投稿)      (セルフ: 採用項目を修正)
```

## ファイルレイアウト

同じPRに対して複数回レビューを回す運用があるため、**1レビュー実行 = 1ランディレクトリ**とする:

```
~/.cache/ai-review/<repo>/pr-<番号>/
  ├─ <run-id>/          # タイムスタンプ(例: 20260726-1530)。ランチャーが作成
  │   ├─ claude.md / gemini.md / codex.md   # 各AIの最終出力(既存統一フォーマット)の複製
  │   ├─ merged.json                        # 統合後の構造化データ(後続スキルの正)
  │   ├─ report.html                        # 人間用ビュー(自己完結単一ファイル)
  │   └─ state.json                         # ブラウザが書くチェック状態
  └─ latest → <最新run-id>/                 # ランチャーが張り替えるシンボリックリンク
```

- ランごとに新規ディレクトリを切るので、掃除不要・ウォッチャーの誤検知なし・前回ランの成果物は無傷・File System Access APIのファイルハンドルも生き続ける。
- 各AIへの出力先パスは**ランチャーが環境変数 `AI_REVIEW_OUTPUT_FILE` としてコマンド前置で明示的に渡す**(スキル側でパス計算させない。真実の源はランチャー1箇所)。環境変数方式なら追加指示引数とのパース衝突がなく、共有コア2ファイルの編集だけで3プラットフォームに効く。
- 保持ポリシー: ランチャーが各PRにつき直近5ランを残して古いランを `trash` する。
- `<repo>` はリモートslugなど衝突しない形で解決する(実装プランで確定)。

## コンポーネント

### 1. レビュー結果のファイル書き出し(3AI共通改修)

- `ai/common/pr_review_core.md` と `ai/common/pr_review_subagents/orchestrator_core.md` に、環境変数 `AI_REVIEW_OUTPUT_FILE` が設定されていれば最終出力をそのパスへも書き出す指示を追加。未設定(スキル単体起動)なら書き出しをスキップして従来通り動く。
- 起動モードの前提: Claude(`--dangerously-skip-permissions`)、Codex(`--dangerously-bypass-approvals-and-sandbox`)、Gemini(`gm-pr-review` / `gm-pr-review-subagent` とも `--approval-mode yolo`)の全レビュー起動で書き込み可能なことを確認済み。モード変更は不要だった。
- Codex/Gemini(生成スキル)は再生成 + `verify_ai_skill_generation_idempotency` による冪等性検証が必要。
- CLAUDE.mdのスキル構成表(core file(s) / adapter-head bits)を同一コミットで更新。

### 2. review-merge スキル(Claude / Codex、共有コア)

- 入力: ランディレクトリの `claude.md` / `gemini.md` / `codex.md`(存在するものだけ。1つでも動く)。ランディレクトリは自動チェーンから渡されるか、手動起動時は `latest` を既定で解決。
- AIの責務は**意味的な重複判定と統合サマリー作成のみ**。同一指摘は1項目に統合するが、**各AIの原文は消さず全て保持**する(統合項目内に検出元ごとの原文ブロックを併記)。
- **ラウンド間引き継ぎ**: 同一PRの前回ラン(あれば)の `merged.json` + `state.json` を読み、新ランの統合項目と突き合わせる。前回「対象外」にした指摘と同一なら「前回スキップ」、前回「対応する」にしたのに再検出された指摘なら「前回対応済のはず」(修正漏れ検知)のマークを merged.json に付与し、HTMLにバッジ表示する。前回ランが無ければ引き継ぎなしで動く。PRコメント投稿済みの指摘は既存レビュースキルの既存コメント重複除外が抑制するため対象外。
- 出力: `merged.json`。統合項目ごとに: 統合連番、file:line、領域、統合優先度(検出元の最高値)、統合サマリー、検出元リスト(AI名、元番号、元優先度・影響度・信頼度、原文)。
- HTMLはAIが書かない: リポジトリ内の決定的なレンダリングスクリプト(Python)が `merged.json` → `report.html` に変換する。テンプレートはスクリプトに内蔵(単一ファイルで配備が単純)。
- 生成後、report.html をChrome系ブラウザで開く(状態保存がFile System Access API前提のため。HTMLセクション参照)。
- シェルに `review-merge` 起動関数を追加(既存 `review` 系と同じ流儀で、herdr/tmux両対応)。通常は自動チェーン(下記)から起動されるが、救済用に手動起動も可能。

### 3. report.html(レンダリングスクリプト + テンプレート)

- 自己完結の単一HTML(CSS/JSインライン、外部依存なし、file://で動作)。
- 優先度で色分け(🔴🟡🟢)したカードリスト。検出元AIバッジ(C/G/X、色違い)。複数AI検出はバッジが並ぶ。ラウンド間引き継ぎの「前回スキップ」「前回対応済のはず」バッジも表示。
- カードごと: 折り畳み(GitHub PR風)、「確認した」チェック、「対応する」チェック(2択)。
- 全展開/全折り畳み、確認済みプログレスカウンタ。
- 状態自動保存: File System Access API(初回に保存先を選択、以後チェックのたび `state.json` へ上書き)。**report.htmlはChrome系ブラウザで開く前提**とし、ブラウザ起動は既定ブラウザ任せにせずChrome系を明示指定する(具体コマンドは実装プランで確定)。初回の保存先選択を行わなかった場合の保険はフッターの番号コピー→スキル引数。
- 固定フッター: 採用済み番号のコマンド文字列(例: `対応: 3,5,8`)+コピーボタン(保険)。

### 4. review-post / review-fix スキル(Claude / Codexのみ、共有コア)

共通動作: ランディレクトリ(既定は `latest`、明示パス指定も可)の `merged.json` + `state.json` を読み、「対応する」項目を抽出 → 一覧提示して確認 → 実行。番号を引数で渡した場合はそちらを優先(state.jsonが無くても動く)。`state.json` はランディレクトリ直下から読む。

- **review-post**: 採用項目をPRコメント投稿。投稿作法(インラインコメント形式、コミットずれ時の再アンカー、改行安全性、投稿前確認)は既存 `pr_comment_post_core.md` の資産を再利用する(共有フラグメント化するか参照構成にするかは実装プランで確定)。
- **review-fix**: 採用項目を修正実装し、完了後に差分サマリーを提示。

Geminiには新規スキルのアダプタを作らない(書き出し改修のみ対象)。

### 5. 自動チェーン(完了監視 → review-merge 自動起動)

既存の `review` / `review-subagents` シェル関数に組み込む(常時有効、`--no-merge` 的なフラグでオプトアウト可能)。

`review-all` はもう使われていないため、この実装で関連ヘルパー(`_review_all_tmux` / `_review_all_herdr` / `review-all`)ごと削除する。

- 起動時にタイムスタンプ付きの新規ランディレクトリを作成して `latest` リンクを更新し、保持ポリシー(直近5ラン)を超えた古いランを `trash` する。ランごとにディレクトリが分かれるため、staleファイルによる誤検知は構造的に起きない。
- **Claudeも新規タブで起動する**(挙動変更: 従来はコマンドを打った現在タブがClaudeセッションになっていた)。
- コマンドを打った元のタブでは、フォアグラウンドのウォッチャーが数秒間隔でランディレクトリ内の結果ファイルの揃いをポーリングする。
  - 待つ対象は**ランチャーが実際に起動したAIの集合**(引数で受け取る)。構成変更に追従する。
  - 進捗を表示する(例: `claude ✓ / gemini … / codex …`)。中断はCtrl-C。
  - 途中でAIが質問待ちで止まるケースは既存の通知フックがユーザーに知らせる。ウォッチャーは待ち続ける。
- 全ファイルが揃ったら、同じタブでそのまま review-merge(Claude)を起動する。
- 救済ルート: 一部AIが失敗した場合はCtrl-Cで中断し、`review-merge` を手動起動すれば存在するファイルだけでマージできる。

## エラーハンドリング

- 結果ファイルが1つも無い場合: review-merge はエラーメッセージで停止(ランディレクトリのパスを提示)。
- `state.json` 不在で番号引数も無い場合: review-post / review-fix は利用可能な項目一覧を提示して番号入力を促す。
- レビュー実行とマージ/投稿の間にPRのheadが進んだ場合: 既存 `pr_comment_post_core.md` の再アンカー規約に従う。
- merged.json と state.json の項目数不一致(古いstate): 不一致を報告し、続行可否を確認。

## テスト

`python3 -m unittest discover -s tests` に統合。

- レンダリングスクリプト: 0件 / 1件 / 全優先度混在 / 複数AI検出 / HTML特殊文字を含む指摘 / ラウンド間引き継ぎバッジあり、のテーブル駆動テスト。
- merged.json スキーマの境界(検出元1〜3、原文欠落なし、引き継ぎマークの有無)。
- ランディレクトリ管理(作成・latest更新・保持ポリシー)のシェル関数テスト(既存のPython経由シェルテストの流儀)。
- 既存の生成系検証(スキル再生成の冪等性)は既存の仕組みに従う。

## スコープ外

- Geminiへの review-merge / review-post / review-fix アダプタ。
- 既存 `pr-comment-post` スキルの廃止(当面併存)。
